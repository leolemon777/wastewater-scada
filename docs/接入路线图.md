## 要解决的问题

当前前端是**纯本地演示**：`src/store/demoScenarios.ts` 每 3 秒生成假数据写入 Zustand store，3D 场景和集控页面都读 store。

目标：把现场真实数据（7 罐体 C# 上位机、多台 M100、后续 PLC/仪表）接入，替换演示数据，最终现场能实时监控和下发控制。

## 目标架构

```
7罐体设备 ──→ C# 罐体上位机(Tank Controller)──┐
   (本地自动闭环)                                │
                                                 ├─→ SCADA Hub ──→ Web 前端(本项目)
多台 M100(网桥/网线)──────────────────────────┤   (唯一出口)      │
                                                 │                    ↓
M100 内置 4G ──→ 有人云/有人组态(独立链路)       └─                  useScadaStore
   (保持启用,不改动)                                                  ↑
                                                                真实数据替代 demoMode
```

三条铁律：

1. **Web 前端不直连任何设备**（M100 / C# 上位机），只连 SCADA Hub。
2. **控制命令必须经 Hub**：确认、限频、超时回读、失败兜底。前端按钮改成「先发命令、等状态回读再更新 UI」，不做乐观更新。
3. **M100 内置 4G 走有人云**是独立链路，与本地总控互不影响，保持现状。

## 三个服务角色

| 角色 | 职责 | 现状 |
| --- | --- | --- |
| **SCADA Hub** | 唯一数据汇总中心；统一归一化；对前端 REST/WS；控制命令确认/限频/回读；日志报警 | 待开发，技术栈待定 |
| **Tank Controller** | 7 罐体自动加水/加酸/液位/pH 闭环；上报状态；受高级命令 | C#（已定方向） |
| **M100 Adapter** | 读 DI/DO/AI；执行 DO 控制；点位映射为标准 tag | Hub 内部模块，接口已验证 |

## M100 现场已验证信息

- 管理 IP `192.168.0.7`；读 IO `http://192.168.0.7/ioread.cgi?read`；写 DO `http://192.168.0.7/iowrite.cgi?do01=1`
- DO 物理输出正常（实测 1 秒级闪烁）
- **不支持 TLS**，不要用 8883 TLS MQTT
- 有人云保持启用，自定义 MQTT 关闭后云端恢复在线
- 当前点表仅 `node0101/0102/0201` + `DO1/DO2`，**不足以映射完整 SCADA**，需真实 PLC/传感器点表
- 多台 M100 必须配不同 IP（`192.168.0.7/8/9/10...`），禁止全用默认 `.7`

## 统一协议要点

- **信封** `scada.v1`：所有消息带 `schema / messageType / sourceId / sourceType / seq / timestamp / quality / payload`
- **质量分级**：`good` / `stale`(通讯异常 >5s) / `offline`(>15s)
- **设备 ID**：罐体 `tank-01..07`、M100 `m100-01..`
- **Tag 命名**：`tank-01.level`、`tank-01.ph`、`m100-01.do01`、`m100-01.ai01`
- **报警**：统一由 Hub 生成（源离线、急停、液位高高/低低、pH 超限、加酸泵故障、DO 写入失败、命令超时等）

## 前端要新增/改造的文件

按 [`M100本地上位机接入上下文.md`](../M100本地上位机接入上下文.md) 的建议：

```
src/services/scadaRealtimeClient.ts   # 连 Hub 的 WS/REST,接 scada.patch 增量更新
src/store/tagMapping.ts               # 真实 tag → 前端 equipmentId 字段映射
```

**数据写入入口**（已存在于 `src/store/useScadaStore.ts`，真实 adapter 复用同一套）：

- `updateEquipment(id, patch)` — 单设备更新
- `setEquipments(equipments)` — 批量替换
- `setKPI(inflow, outflow, power)` — 总进水/出水/能耗
- `setDemoMode(false)` — 接入真实数据时关掉 demo tick

**映射示例**（完整表见 [`总控统一数据协议.md`](总控统一数据协议.md) 数据映射规则）：

| 来源 tag | 前端设备 | 字段 |
| --- | --- | --- |
| `tank-01.level` | `tk-collection-1` | `levelValue` / `levelPercent` |
| `tank-01.ph` | `tk-ph1` | `pH` |
| `m100-01.do01` | `p-lift-1` | `runStatus` |
| `m100-01.ai01` | 待定 | 待现场点表确认 |

## Hub 对前端的接口

```
GET  /api/scada/snapshot              # 全量快照
WS   /ws/scada                        # 实时推送
```

WS 事件类型：`scada.snapshot` / `scada.patch` / `scada.alarm` / `scada.commandAck` / `source.status`
前端接到 `scada.patch` 后只更新变化的设备和 KPI。

## 开发顺序（源自协议文档）

1. 先开发 SCADA Hub 本地后端骨架
2. 加 M100 最小接口：状态、IO 读取、DO 控制
3. 加 C# 罐体协议模拟器，用假数据模拟 7 个罐体
4. 前端接入 `/api/scada/snapshot` 和 `/ws/scada`
5. 开发真实 C# 罐体上位机
6. 接入真实 M100 多设备配置
7. 根据现场点表完善 `tagMapping`

## 待决策点

动手前需先定，影响后端选型和前端 adapter 写法：

- **Hub 后端语言**：Node.js（与前端同栈、部署轻）/ Python（协议解析强）/ C#（与罐体上位机同栈、Windows 原生）/ Go（单二进制）
- **第一版接哪条链路**：M100 IO（已验证、最快出成果）/ C# 罐体模拟器（跑通完整闭环）/ 两条并行
- **Hub 部署形态**：现场电脑手动启动 / Windows 服务常驻
- **真实点表状态**：已有 / 整理中 / 先搭框架（影响能否把真实数据真正接进来）
